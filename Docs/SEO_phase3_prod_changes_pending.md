# SEO Phase 3 — pending changes for production

Phase 3 (structured data, lighter media, CMS redirects, measurement — see
`src/lib/structured-data.ts`, `src/lib/site-settings.ts`, `src/lib/images.ts`,
`scripts/optimize-media.mjs`, `src/integrations/nginx-redirects.mjs`,
`src/components/Analytics.astro`, `nginx.conf`) is built and works against local
mocks. This file is the checklist for go-live — work through it alongside
`Docs/SEO_phase1_prod_changes_pending.md` and
`Docs/SEO_phase2_prod_changes_pending.md`. Later phases get their own
`Docs/SEO_phaseN_prod_changes_pending.md` file; don't merge them into this one.

## Backend (policrafters-cms)

- [ ] **Backend: expose the company's data at `GET /api/site-settings`.**
  What: a Wagtail global setting (legal name, phone, addresses, opening hours,
  area served, DBPR license number, certifications, social links, logo)
  exposed as `{ type, title, locale, meta, fields }` per `Docs/API_CONTRACT.md`
  "SiteSettings".
  Where: the CMS repo. Frontend loader: `src/lib/site-settings.ts`
  (`PUBLIC_SITE_SETTINGS_API_URL`).
  Why: today the JSON-LD runs on a mock holding only what the site already
  shows (name, phone, one Medley address, logo). Hours, area served, license,
  certifications and social links are empty, so those fields are simply not
  published.
  How to verify: with `PUBLIC_USE_API=true`, build with
  `PUBLIC_ALLOW_INDEXING=true` and read the `application/ld+json` block in
  `dist/index.html` — it should carry the CMS values.

- [ ] **Confirm the company data BEFORE loading it.**
  What: decide the one true phone, address(es), hours, service area and license.
  Why: in the test data the four contact addresses are the same
  (7735 NW 75th Ave, Medley), and the phone is `(813)` — a Tampa area code —
  while the address is in Miami-Dade. Google and AI assistants cross-check
  these against other sources (Google Business Profile, directories), so they
  must match exactly everywhere. `src/components/Footer.astro` and
  `src/mocks/contact-page.*.json` still hardcode the same values; once
  confirmed they should read from site-settings (not done now: no design or
  copy changes in this phase).
  How to verify: compare the JSON-LD `telephone`/`address` with the Footer, the
  contact page and the Google Business Profile.

- [ ] **Backend: image `width`, `height` and `renditions`; `alt` required.**
  What: every image object gets optional `width`, `height` and
  `renditions: { "<width>": "<url>" }` (WebP, Wagtail renditions), and `alt`
  becomes mandatory on upload. See `Docs/API_CONTRACT.md` "Imagen extendida".
  Where: the CMS repo. Frontend: `src/lib/images.ts` (`resolveImage`) already
  understands the extra fields.
  Why: local files get responsive WebP from `scripts/optimize-media.mjs`, but
  CMS images do not. **Note:** the `src/lib/*-content.ts` loaders currently
  keep only `{ url, alt }` from each image, so when the backend ships
  `renditions` they must be passed through to `resolveImage` (small change per
  loader/view) before CMS images benefit.
  How to verify: a CMS hero image renders with a `srcset` pointing at the
  `.webp` renditions and declared `width`/`height`.

- [ ] **Backend: enable `wagtail.contrib.redirects` and expose `GET /api/redirects`.**
  What: the module's list as `fields.items: [{ old_path, new_path, is_permanent }]`
  per `Docs/API_CONTRACT.md` "Redirects".
  Where: the CMS repo. Frontend: `src/integrations/nginx-redirects.mjs`
  (`PUBLIC_REDIRECTS_API_URL`).
  Why: when an editor changes a URL, the old one must answer 301 instead of 404
  (needed for Phase 4, when `model-1` slugs get real names).
  How to verify: add a redirect in Wagtail, rebuild, check
  `nginx/redirects-301.map`, then `curl -I https://<host>/<old-path>` →
  `301` with the new `Location` (in Spanish too: `/es/...`).
  **Not tested here:** Docker was not available in the environment where this
  was built, so `nginx.conf`'s new `map`/`if` blocks and the Dockerfile `COPY`
  were never run in a container — run `docker build` and
  `docker run … nginx -t` once before deploying.

- [ ] **Backend: set the new `PUBLIC_*_API_URL` values on the build host.**
  `PUBLIC_SITE_SETTINGS_API_URL` and `PUBLIC_REDIRECTS_API_URL` (see
  `.env.example`). Redirects only reach nginx on a rebuild of the site, since
  they are generated at build time.

## Measurement

- [ ] **Create the GA4 property and set `PUBLIC_GA4_MEASUREMENT_ID`.**
  What: the `G-XXXXXXXXXX` ID, set on the production build host.
  Why: `Analytics.astro` renders nothing unless the ID is valid AND
  `PUBLIC_ALLOW_INDEXING=true`, so staging can't pollute the property.
  How to verify: open the production site with GA Realtime open.

- [ ] **Verify the domain in Google Search Console and Bing Webmaster Tools; submit the sitemap in both.**
  What: either DNS verification, or set `PUBLIC_GOOGLE_SITE_VERIFICATION` /
  `PUBLIC_BING_SITE_VERIFICATION` to the content of the meta tag each tool
  gives (rendered by `SeoHead.astro`). Then submit
  `https://policrafters.com/sitemap-index.xml` in both.
  Why: the baseline for Phase 4 — impressions, clicks, indexed pages.

- [ ] **Take the production Lighthouse baseline and track the targets.**
  Targets (Google's "good"): LCP < 2.5 s, CLS < 0.1, INP < 200 ms.
  Local baseline measured with Lighthouse 12, mobile emulation, `astro preview`
  (single run each, so ±0.3 s noise), `origin/main` → this branch:

  | Page | Score | LCP | Page weight |
  |---|---|---|---|
  | `/` | 70 → 87 | 27.7 s → 3.5 s | 37.7 MB → 0.86 MB |
  | `/collections` | 92 → 93 | 2.5 s → 2.6 s | 0.71 MB → 0.11 MB |
  | `/services` | 90 → 93 | 3.0 s → 2.4 s | 0.37 MB → 0.13 MB |
  | `/collections/shower-doors/fixed/model-1` | 77 → 94 | 5.4 s → 2.4 s | 1.09 MB → 0.20 MB |

  CLS was 0 and TBT 0 ms everywhere. The homepage LCP (3.5 s) is still above
  the target; FCP is ~2.4 s on every page, which points at the render-blocking
  Google Fonts stylesheet in `PageLayout.astro`/`HomePage.astro` (self-hosting
  Arimo would likely fix it — not done: out of Phase 3's scope).
  INP can't be measured in a lab run; read it from Search Console's Core Web
  Vitals report once there is field data.

- [ ] **Prune the original heavy files from `public/`.**
  What: `dist/` still ships both the originals (`public/images` 85 MB,
  `public/videos` 132 MB) and the optimized copies in `dist/_media/` (84 MB).
  Pages no longer reference the originals, but they stay reachable by URL.
  Unreferenced candidates for deletion (owner to decide): `public/videos/hero.mp4`
  (65 MB, not used anywhere), most of `public/images/projects/*`,
  `public/images/brands/brandx.svg`, `falper.svg`, `public/images/hero-fallback.svg`,
  `public/images/pages/fixed_door_shower_black_white_new.png`.
  Why: smaller Docker image and no 65 MB file to crawl. Check the CMS doesn't
  reference any of them first.

- [ ] **Note: the media pipeline runs on every build.**
  `npm run build` runs `scripts/optimize-media.mjs` first (`prebuild`). The
  first run on a clean machine takes a few minutes (video encoding); after
  that it only re-does files whose source changed. `public/_media/` and
  `src/data/media-manifest.json` are generated and gitignored. The build host
  needs Node 22 and the dev dependencies (`sharp`, `ffmpeg-static`).
